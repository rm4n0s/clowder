# Security

This file records the security reviews of Clowder: of 1.0 (step 13.2, 2026-10-27) in the first part, of what 1.1 added (step 17.1, 2026-10-27) in the part "Clowder 1.1", and of what 1.2 added (step 24.1, 2026-10-29) in the part "Clowder 1.2" at the end: what was reviewed, what was found and fixed, what is accepted, what is out of scope, and how to report a vulnerability. The decisions the first review led to are D36 and D37 in `docs/SPEC.md`; those of the second are D47 and D48, and the third is D66.

## How to report a vulnerability

Open an issue in the GitHub repository of the project (`github.com/rm4n0s/clowder`) with the label "security", and say what you found and how to repeat it. Do not put a working exploit against a live installation in a public issue: say in the issue that you have details, and the repository owner will tell you where to send them. You can also contact the repository owner through their GitHub profile. There is no security mailing list.

## What was reviewed

Every route of `internal/web/server.go` (73 patterns) and every service method it reaches, in this order:

- **Access.** Every route that needs a session has one (routes are protected unless marked `optionalSession` or `noSession`). Every service method takes the acting user and checks the permission itself. A private room, a post in it, its board, its files, a private conversation and its messages are the 404 page to anyone who is not a member, admins included (SPEC D29, §7.11). The admin pages are the 404 page to members. Edit and delete are for the author, or for an admin where SPEC §7.3 and §7.2 say so. The IDs of a path, a query and a form were checked to belong to the parent they come with: a card, a column or a member of another room, a file of another post, a message to reply to from another conversation, a message of a conversation the user is not in.
- **Streams.** Each stream checks access when it subscribes and again for each event it renders (it reads through the services as its user); a user who loses a room or a conversation is sent away and gets nothing more; `Last-Event-ID`, `seen` and `before` are only IDs used as cursors inside the room or conversation that was already checked.
- **Sessions and cookies.** `HttpOnly`, `SameSite=Lax`, `Secure` unless the base URL is `http://`. Session and invitation tokens are 32 random bytes; the database keeps only their SHA-256. Login makes a new token every time (no fixation); logout deletes the session on the server; disabling a user deletes their sessions.
- **Cross-origin protection.** `http.CrossOriginProtection` wraps every route: a state-changing request that the browser marks cross-site, or whose `Origin` is not the host, is a 403, for forms, Datastar requests and multipart uploads alike.
- **Headers** of every answer, including errors and streams.
- **Uploads.** Limits are enforced while the file is read; names are cleaned; storage keys are random 64-character hex strings and nothing else can name a file; only PNG, JPEG, GIF and WebP are served inline, everything else is an attachment of type `application/octet-stream`; temporary files are removed on every failure and when the server starts.
- **Output.** Every `templ.Raw` and `template.HTML` (listed below); markdown in goldmark's safe mode; search snippets; mention links; message bodies; every `data-*` expression that holds a value.
- **Authentication.** The login limiter, argon2id, invitations, sign-up, password lengths.
- **Input limits, the server's timeouts, shutdown, the log, and the dependencies.**

## Accepted risks and things to know

- **`'unsafe-eval'` in the policy.** Datastar compiles the `data-*` expressions of the page with `Function`. The policy still refuses every inline script and every script from another site, which is what an injected element needs.
- **Images from other sites.** A markdown body may embed an image from any `http` or `https` address (SPEC §7.3), so the policy allows such images, and the author of a post can see the address of whoever opens it (no `Referer` is sent). Turn it off by changing `img-src` in `internal/web/security.go`.
- **A user can lock a username out.** Five failed logins for a username block that username for 15 minutes from every address (SPEC §7.1). The address limit stops one client from trying many usernames. The limiter is in memory: a restart forgets it.
- **`-trust-proxy`.** Behind a proxy, the address limit works only with `-trust-proxy` and only when every request comes through the proxy. Without it every client has the proxy's address.
- **Opening a conversation or the notifications page marks them read** (SPEC D33, §7.9). A cross-site link to one marks it read for a logged-in member. It changes nothing else, and no other `GET` route changes state.
- **Downloads are cached by the browser of the reader for a day** (`private, max-age=86400`). A member who was removed from a room can still open a file they had opened in the same browser, until it expires.
- **Admins** cannot read private rooms or conversations, but can rename and delete any room and remove any member (D29), and see names and summaries in the audit log.
- **Names are public inside the installation.** Every user can list every enabled user (to add them to a room or a conversation), so usernames are not secret.
- **Attachments are not scanned.** A file is stored as it came. It is served as a download with `nosniff` and a sandboxing policy, and inline only when its content is a valid PNG, JPEG, GIF or WebP.
- **One process per database**, and a full disk or a copy of the data directory is outside what the program can protect.

## Out of scope

- **TLS.** Clowder speaks plain HTTP. The reverse proxy terminates TLS and must pass the `Host` header (the README has examples for Caddy and nginx). Without TLS a password and a session cookie cross the network in clear text.
- **Email.** There is none: invitation links are handed over by an admin, and there is no password reset. A person who forgets their password needs an admin to disable the account and invite them again.
- **Two-factor authentication, single sign-on and passkeys** (SPEC §2).
- **End-to-end encryption.** The server can read every message, and so can whoever has the data directory.
- **Denial of service of the machine.** Limits on request bodies, headers, forms, passwords, hashes and streams are set, but a flood of requests is for the proxy or the firewall.
- **The host.** File permissions of the data directory beyond the program's own, backups and who has a shell on the machine.
- **Hostile administrators.** An admin is trusted with the installation.

# Clowder 1.1

The review of step 17.1 (2026-10-27) covers everything 1.1 added: the REST API (`internal/api`, 63 routes) and its WebSocket, the bearer tokens, PostgreSQL, Redis and the several-processes mode (`internal/store`, `internal/cluster`), the upload staging, the Docker image, `compose.yaml`, `compose.cluster.yaml` and the Caddyfile. It was done the way the first one was: every route and every service method it reaches was read, the claims below were turned into tests wherever a test can state them, and the tests were run on PostgreSQL and Redis too (`scripts/test-docker.sh`).

## What was reviewed

- **Every API route and the WebSocket.** Each handler takes the acting user from the bearer token (`authenticated`, which wraps every route but `login`, `signup`, `invitations/{token}`, `openapi.json` and the catch-all), calls one service method that checks the permission itself, and has no other way to the data. `TestEverySecuredRouteIsListed` fails when a route that needs a login is missing from the table, and `TestWhoMayCall` sends every one of the routes with no header, an empty bearer, another scheme, an unknown token, an expired one, a browser session's token, the session cookie alone, a disabled user, a member and an admin. A private room, a post, board, file or member list in it, and a private conversation, its messages and files are `404` to non-members, admins included; the admin routes are `403` to members. IDs in paths, queries and bodies that name something of another parent were checked (the upload of another user, an attachment of another post kept on an edit, a task of another post in an edit, a reply to a message of another conversation, a column or card of another room): each is refused by the service, with the same tests as the pages (`TestUploadsOfAnotherUserAreRefused`, `TestPatchPostMistakes`, `TestMessageRoutesOfTheErrors`, `TestRoutesOfTheErrorsOfTheBoard`).
- **Mass assignment.** Every body is decoded with unknown fields refused (`422`, the field named), and no body struct has a field for something the user must not set (no role at sign-up, no owner, no visibility on a room patch). `TestRequestSchemasHaveTheFieldsOfTheStructs` ties the structs to the document, which says `additionalProperties: false`.
- **Limits and numbers.** A JSON body is at most 64 KiB (`http.MaxBytesReader`), the feed, notification and message limits are 1 to 100, positions are clamped by the service, a search page after the 1000th is empty, an audit page is capped, topics are at most 200 per WebSocket and a WebSocket message at most 16 KiB. Deep nesting, numbers out of range, NUL and invalid UTF-8 are `422`, never a panic or a 500 (`TestHostileJSONBodies`). An ID above the range of the databases was a finding (S9).
- **Tokens.** 32 random bytes (43 characters of base64url) from `crypto/rand`; the database keeps only the SHA-256, and the lookup is by that hash (a lookup in a unique index, so no secret is compared byte by byte); a login makes a new token every time; the kind of the session is checked on both sides (the cookie of a page is not a bearer token, a bearer token is not read from a cookie, `TestWhoMayCall`, `TestAPIIgnoresThePageCookie`); the lifetime is the configured one from the last use; a disabled user, a logout, ending a session from the list and an expiry end it (`TestAnExpiredTokenIsDeleted`, `TestEndSession`, `TestLogout`, `TestAdminPatchUser`); a role change reads the role again with the next request and closes the sockets (`TestWSSessionChanges`). A token is never logged: the request log has the route pattern, the status and the user ID, never the header, the path of an unmatched request is cut and the invitation token is replaced; error metadata holds no token; the WebSocket never takes one in the URL. `TestNoSecretsInTheLog`, `TestNoTokenInAnyAnswerOrLog` and `TestWSLogs` search the log and the answers for the token, the password and the header after the routes were used, also the failing ones.
- **The login limiter.** `/auth/login` counts failures per username and per address with the limiter of the pages (5 in 15 minutes; in Redis when a Redis is set; `TestLoginLimiter`, `TestAPILoginUsesTheClientAddress`, `TestLoginCounterOnRedis`); the answer is `429` with `Retry-After: 900`. `/auth/signup` and `GET /auth/invitations/{token}` are not limited: see the accepted risks.
- **JSON answers and headers.** Every answer of the API goes through the same `secureHeaders` as the pages (D36): `Content-Security-Policy`, `nosniff`, `Referrer-Policy`, `X-Frame-Options`, `Cross-Origin-*`, `Cache-Control: no-store` (and HSTS for an https base URL), the JSON content type has a charset, there are no CORS headers at all (an `OPTIONS` request is a `405` without `Access-Control-*`), and the cross-origin protection of the pages covers the API's unsafe methods, so a web page of another site cannot send a state-changing request even with a token (`TestAPIThroughTheServer`, `TestAPIPostsAreProtectedAgainstOtherSites`). Errors never repeat the input; a `500` says nothing about the cause and the cause is logged with its route (`TestInternalErrorIsLoggedAndHidden`, `TestPanicIsAJSON500`).
- **Uploads.** The size limit is enforced while the file is read (`TestUploadBodyIsCutEarly`), the form must hold the one file and nothing else, a file stored before the rest of the form was found wrong is removed again, names are cleaned and storage keys are 64 random hex characters (a key from a client is checked with `validKey` before the disk is touched: `TestBadKeys`, `TestNotesRefuseBadKeys`, so `../` and absolute paths never reach a path), the note that binds a staged upload to its owner is written whole and renamed, an upload is attached once and only by its owner (`TestUploadsOfAnotherUserAreRefused`, `TestUploadIDsThatAreNotUploads`), the sweep removes what no post took after a day and a download has the headers of the pages' download (`nosniff`, a sandboxing policy, only four image types inline: `TestDownloadHeaders`).
- **The WebSocket.** The token is checked before the upgrade; the library's origin check is on (`TestWSHandshake` sends another site and gets `403`); compression is not negotiated (`TestWSDoesNotNegotiateCompression`), so a message cannot be a bomb inside the 16 KiB read limit; a message over it, a binary frame and text that is not one JSON value close the connection (`TestWSMessagesThatCloseTheConnection`); topics are checked on subscribe and again for every event, for the user (`TestWSEventsReachOnlyTheSubscribers`, `TestWSLosingAccess`), the sockets end at once on logout, disable and role change and at the next ping when the session expired (`TestWSSessionChanges`, `TestWSExpiredSessionEndsAtThePing`); a slow client gets `resync` and is closed instead of blocking the hub (`TestWSOverflowSendsResync`); a client that does not answer pings is closed (`TestWSClientThatDoesNotAnswerPingsIsClosed`); the server closes every socket with 1001 on shutdown and waits for them (`TestWSServerShutdown`).
- **PostgreSQL and Redis.** Every statement with a value uses a parameter (`grep` of `Raw(`, `Exec(` and the builders of the search: the only text concatenated into SQL are table and column names that are constants of the code and `quoteIdent` of the model's own names; the search query is passed as a parameter to `to_tsquery` after it was made safe, and `TestSearchNeverFailsOnOddQueries` throws the syntax of FTS5, `tsquery`, `LIKE` and SQL at it on both databases). The URL of the database and of Redis is shown only with its password replaced by `xxxxx` (`config.RedactURL`, used by every log and every error metadata), an unparseable URL is replaced altogether, and the error of the driver for a URL that cannot be parsed is dropped because it quotes the URL (`TestOpenPostgresFailures` in `internal/store/postgres_test.go`, `TestOpenStoreLogsTheURLWithoutItsPassword`, the Redis tests of `internal/cluster`). A usage text that printed it was S10. The events on Redis hold a topic and IDs only, never text (`wireEvent`), the keys of the login limiter hold a hash of the username or address, never the text (`TestCounterKeyIsSafe`), a message on the channel that is not an event is dropped and logged without its content (`TestMalformedMessagesAreSkippedAndLogged`).
- **The database user's rights** were tried with real roles (a superuser, the owner of the database, a role with `CREATE` on the database and the schema, and a role with nothing): see the README, "PostgreSQL without Docker". The owner and the role with the two grants migrate and run; the role with nothing fails to migrate with "permission denied for schema public". The Redis user's commands were tried the same way (README, "Redis").
- **Docker.** See "The Docker files" below.

## Accepted risks and things to know (1.1)

- **Sign-up and the invitation check were not rate limited. Handled in 1.2 (step 23.3, D62), the sign-up only.** `POST /auth/signup` and the sign-up form of the pages now count a sign-up whose invitation token is unknown, used or expired as one failed login of the client address, in the same counter as a wrong password (in Redis when several processes share a database, so the limit holds across them). After 5 in 15 minutes the sign-up answers `429` (`rate_limited` with `Retry-After` in the API, the message "Too many attempts" in the form) before it looks at the invitation, and a login from that address is `429` too; a valid invitation never counts, so mistakes in its form cannot lock an address out. `GET /invite/{token}` and `GET /auth/invitations/{token}` are still not limited: they only say whether a link is valid, and guessing a token (32 random bytes, 256 bits, looked up by its SHA-256) is hopeless however many tries there are; a wrong token costs one indexed query and no password hashing. A flood of requests is for the reverse proxy. Tests: `TestSignUpCountsInvalidInvitations`, `TestSignUpWithAValidInvitationDoesNotCount`, `TestSignUpFailuresAreSharedThroughRedis`, `TestSignUpLimitOnThePage`, `TestSignupLimitOnTheAPI`.
- **No limit on the number of WebSockets or of open streams per user. Handled in 1.2 (step 23.3, D62).** A user holds at most 30 live connections in one process: the event streams of the pages, the user's WebSocket of the API and the signalling sockets of calls together. The 31st is refused before it starts, with `429` and `Retry-After: 30` (the API's answer has the error `rate_limited`); a stream or socket that ends, in any way, gives its place back. **The count is per process, not per installation:** with several processes behind a load balancer a user may hold 30 on each, and the load balancer's own limits are the operator's. A page holds one stream (the pages that have none of their own open the sidebar's `/me/stream`), so about 30 open pages fit. The Datastar client retries a refused stream with a growing wait (1 s, 2 s, 4 s, up to 30 s), so the limit does not make a tight loop. Tests: `TestConnectionsAcquire`, `TestStreamsOfAUserAreLimited`, `TestStreamsAndSocketsShareTheLimit`, `TestCallSocketCountsAndIsLimited`, `TestWSConnectionsAreLimited`, `TestCallSocketIsLimitedAndGivesItsPlaceBack`.
- **No limit on what a user has staged. Handled in 1.2 (step 23.3, D62).** A user may have staged (uploaded with `POST /uploads` and not yet attached) at most ten times the attachment limit in bytes, 250 MB by default, counted from the notes that exist in the files directory (so the uploads of every process count, and nothing is counted twice). An upload that would go past it is removed again and answers `413 too_large` with a message that says to post the staged files first. Posting the files, a post that is refused, and the hourly sweep that removes uploads older than a day free their bytes. The pages stage nothing (their files travel with the post in one request), so only the API is concerned. The count reads every note of the directory on each upload, which is cheap for the numbers a limit of this size allows. Tests: `TestPostsStagedLimit`, `TestPostsStagedLimitOfParallelUploads`, `TestUploadStagedLimit`.
- **A client made of a web view cannot call the API.** The cross-origin protection of the pages also covers the API (D43 said it was not needed): a state-changing request with an `Origin` other than the host is `403`. This is a safety property; a desktop client must send the request from its native HTTP stack. `docs/API.md` says so.
- **A download is cached for a day by the client** (`private, max-age=86400`), as on the pages: a member removed from a room can open a file they already have until it expires.
- **API sessions are not counted.** Every login makes a session row; a user who logs in in a loop makes many. They expire with the rest, the user's own list shows them, and the hashing of every login is bounded (S4), so the rate is low.
- **The `html` of the answers is the server's output, to be trusted as the pages trust it.** A client that renders it must apply its own policy as well (`docs/API.md`).
- **Redis without a password inside the compose network.** Anyone who gets a connection to that Redis could publish events (forcing page reloads, closing sockets with `user.changed`) and clear the login counters. The events carry no text. The README says to give any other Redis a password, ACL and TLS.
- **Mutable image tags** (above) and no scan of the image: the operator pins digests if they need to.
- **`sslmode`.** The driver's default is `prefer`; the README says to use `verify-full` or `require` beyond a private network, and compose uses `disable` inside its own network.
- **`/healthz` and `/api/v1/openapi.json` need no login.** The first says `ok` or `unavailable`; the second describes the API, which is open source.
- **`/manifest.webmanifest` and `/sw.js` need no login** (step 21.5, D58): a browser fetches the manifest without cookies, and a service worker is fetched by the page that registers it. The manifest holds the name and the icons of Clowder and the source of the worker holds no secret; both are the same for everyone. The worker caches the files of `/static/` only and never answers a page, an API call, a file or an avatar (`TestServiceWorkerSourceRules`), so nothing private is kept by it. Both are sent with the headers of D36 (`TestManifest`, `TestServiceWorkerIsServed`).

# Clowder 1.2

The review of step 24.1 (2026-10-29) covers what 1.2 added: the settings, the avatars, the reset links and the SSH sign-in codes (`internal/sshcode`, `internal/app`), the notification preferences and mutes, the search of private messages, the limits of step 23.3, the service worker and the manifest, the metrics listener, `clowder backup` and `clowder restore`, and the calls (`internal/calls`, a pion media server with a signalling WebSocket). It was done the way the earlier ones were: the code of each item was read as an attacker would read it, what was suspected was tried, the claims below were turned into tests wherever a test can state them, and the tests were run on PostgreSQL and Redis too (`scripts/test-docker.sh`). Two fuzz tests were added and run for more than a minute each (`docs/implemented-proof-images/24.1-fuzz.txt`).

## What was reviewed

- **The SSH server (`internal/sshcode`).**
  - *Authentication.* Public keys only: no password, no keyboard-interactive, no `none`; a certificate matches no registered fingerprint, so it is refused; three tries per connection; the key is looked up by its SHA-256 fingerprint and must belong to the **enabled** user whose name the client gave. A refused key, an unknown user, a disabled user and the key of another user get the same answer (`unable to authenticate`), and the library sends no reason (`TestServerRefusesAuthentication`). Found: S12, the answer to the query "would you take this key?".
  - *Refused requests.* A session channel is the only channel (`direct-tcpip`, `x11` and a second session are rejected); global requests (`tcpip-forward`, `cancel-tcpip-forward`, `no-more-sessions`) are refused; inside the session only `shell` and `exec json` give a code. `pty-req`, `env`, `x11-req`, `auth-agent-req@openssh.com` (agent forwarding), `window-change` and `signal` are refused and the session goes on (OpenSSH sends them before a shell), but after 8 refused requests the session ends; any other `exec`, and `subsystem` (sftp), end the session with the status 1 and one fixed line. Nothing of the client's is run, written or echoed (`TestServerRefusesWhatIsNotACode`).
  - *Resource limits.* 64 connections in all, 8 from one address (S13), 10 s for the handshake (the authentication included), 30 s in all, three authentication tries, the library's own caps (128 authentication messages in all, packets of at most 256 KiB, a 2 MiB window for a channel whose data nobody reads, so a client that sends data on the session can buffer 2 MiB and no more), 8 refused requests. A connection that offered a key and did not get in is one failed login of its address in the limiter of the web login; five block the address for 15 minutes; a connection that offered no key is not counted, so a port scan cannot lock out the web logins of a shared address (`TestServerCountsOneFailurePerConnection`, `TestServerBlocksAnAddressThatFailed`, `TestServerHandshakeDeadline`, `TestServerConnectionDeadline`, `TestServerCapsTheConnections`). A user gets 10 codes in 15 minutes (`TestSSHCodeLimiter`).
  - *The host key.* An Ed25519 key made on the first start in the data directory (or at `-ssh-host-key`), in a temporary file of mode 0600 that is linked into place, so that a reader never sees half a key and two processes that start together end with one key (`TestLoadHostKeyTwoStartsTogether`); `serve` makes the data directory 0750, and the key inside it is 0600. Found: S14, a key that exists with a looser mode.
  - *The log.* A code is never logged: the log of a code has the user, the fingerprint of the key and the address; the `exec` command, the environment and the banner of the client are not logged (`TestServerGivesTheCode` and `TestServerWithTheRealServices` search the log for the code).
  - *Fuzz.* `FuzzParseAuthorizedKey` (`internal/app/sshkeys_fuzz_test.go`, seeds in `internal/app/testdata/fuzz/FuzzParseAuthorizedKey` and in the test) feeds `parseKeyLine`, which `SSHKeys.Add` calls on the text of the form, valid keys of every accepted type, keys that are refused (`ssh-dss`, a short RSA key), lines with options, with two keys, with comments, with NUL, with 100 KB of text and broken base64. It checks that nothing panics or takes long, that a key it returns has a type and a fingerprint, and that its stored normal form parses back to the same key. Run for 75 s with two workers: **918,063 executions, 149 interesting inputs, no failure**. The library caps an RSA key at 16,384 bits (a key of 32,768 bits is refused when it is parsed), so a registered key cannot make the server do a huge modular exponentiation.
- **The sign-in codes.** A code is 8 characters of Crockford's base32 from 40 bits of `crypto/rand` (5 bits for each character, so every character is uniform), shown once and stored as its SHA-256; it lives 60 s, is used once (`ConsumeSSHCode` is one conditional update, so two requests that race with the same code give one login: `TestCodeWorksOnceWhenRacing`), is replaced by the next one, and goes with its key (`DeleteSSHKey`). The comparison is a lookup of the hash in the database, never a byte-by-byte comparison of the secret, so there is nothing to time. A wrong code counts as a failed login of the username **and** of the address in the limiter (five in 15 minutes block both, and a password login too), and a pending login ends at the fifth wrong code. The password step does not clear the failures (only a complete login does), so the password cannot be used to reset the count between guesses. At 40 bits and five tries per 15 minutes the chance of a guess is below 5 in 10^12 for each window of a code; see the accepted risks for the tries that race.
- **The pending login (`clowder_pending`).** 32 random bytes, stored as SHA-256, 5 minutes, `HttpOnly`, `SameSite=Strict`, `Secure` as the session cookie is, `Path=/login` (so it is sent to the login pages only); it gives **no access** by itself: only the right code of that user finishes it, in one transaction that deletes it and starts the session. Another browser that has the cookie value needs the code too; a used, expired or cancelled one, one of a disabled user and one of a user who changed the password are "this sign-in has expired" (`TestCompleteLoginNeedsAPendingLogin`, `TestPendingLoginsEndWithTheAccountChanges`, `TestLoginCodeSubmitFailures`). The `next` path it carries is checked by `safeNext` again when it is used.
- **Reset links and avatars.**
  - *Reset links.* 32 random bytes, stored as SHA-256, 24 hours, used once (`MarkPasswordResetUsed` is conditional), a new link replaces the old; using it sets the password, **ends every session and every pending login of the user** and the call the user is in, and writes the audit event; the link is checked again inside the transaction; an unknown, used, expired or disabled-user link is the same 404 and the log has the reason. The token is cut out of the log of the request (`/reset/{token}`) and the page has `Referrer-Policy: same-origin` and `Cache-Control: no-store`. See the accepted risks for the second factor.
  - *Avatars.* The upload is read up to 2 MiB, its format is found from its **content** (the declared type is never looked at), the size is read from the header before the picture is decoded (4096 by 4096 at most), the Go GIF decoder refuses a frame larger than its screen (so the size of the header is the size of the allocation), the picture is decoded and **re-encoded as a PNG** of 256 by 256 pixels, so a polyglot file (a PNG that is also a script, an archive or a PDF, or a GIF with trailing data) leaves nothing of its second life: only pixels are stored. The file is served with `Content-Type: image/png`, `X-Content-Type-Options: nosniff`, the sandboxing policy of downloads, `Cache-Control: private, max-age=86400` and an ETag of the random key; any logged-in person can read any avatar (as they see every name). A bomb is limited by the size cap, the pixel cap and the two decoding places (`pictureSlots`); the costs are measured in the accepted risks. Tests: `TestSetAvatarImages` (the header-only 100000 by 100000 PNG, the too-wide JPEG, the truncated files, WebP), `TestAvatarServing`, `TestAvatarRouteRefusals`.
- **The settings routes, the mutes, the preferences and the search of messages.** Every route takes the actor from the session and changes only the actor's own rows (the settings, the SSH keys, the sessions: `EndSession` checks the owner); the places of the preferences are checked with the permission of a member (a private room that the user may not read is 404, a visible room that the user has not joined is 403, a conversation of others is 404, a disabled user 401: `TestPrefsPermissions`) and a mute of a place the user cannot see is the same refusal and writes nothing (`TestPrefsPermissions` checks that a refused change saves no row and publishes no event). The rows go with the membership (`TestPrefsEndWhenTheUserLeaves`). The search of messages joins `conversation_members` with `left_at IS NULL` **in the same query** as the match, so it finds only messages of the conversations the user is in now; the paging cursor is only an ID bound (`m.id < ?`) in that query, so a cursor of an older page never shows what the membership no longer shows (the new `TestMessagesSearchPagingAfterLeaving` leaves a group between two pages); admins get nothing more (`TestMessagesSearchPermissions`). Every POST route of the pages is in the tables of `TestEveryPostRouteRefusesCrossOriginRequests` and `TestEveryPostRouteCapsItsBody`, which fail when a route is missing.
- **The limits of 23.3.** The count of the staged uploads reads every note of the files directory on each upload: it is bounded now by the cap on the number of staged files (S15).
- **The service worker, the manifest and the metrics.** `sw.js` caches `GET`s of `/static/` of its own origin and calls `respondWith` once, for them (`TestServiceWorkerRules` reads the embedded file itself, `static.ServiceWorker`, and `TestServiceWorkerCachesOnlyStatic` runs it in Chromium against the pages, the API, a file and an avatar); its scope is the origin (served at `/sw.js`), a `new URL` of the request is normalised before `startsWith('/static/')` is asked, so `/static/../avatars/1` is not a static file; it keeps the cache under a name with the version and drops other versions. The manifest has no secret. The metrics listener is off unless `-metrics-addr` is given, never on the public listener (`/metrics` there is the 404 page), serves `GET /metrics` only, and no label carries an ID, a name or a token: `TestMetricsLabelsNeverCarryIDsOrNames` sends requests with IDs, a username and tokens in the path to the routes of the pages, the API, **the calls of the pages and the call sockets of both** (added in this step), and searches the whole output; the patterns are those of the mux, `none` for what no route matched.
- **Restoring hostile archives.** Beside the cases of 23.1 (`../`, absolute paths, links, devices, FIFOs, a header that declares a huge size, a manifest that lies, a gzip bomb after the end, a manifest that is not first, a newer schema, a target that is not empty) these were tried, each with the target missing and the target empty, and each leaves the target and its parent as they were (`TestRestoreMoreHostileArchives`): a tar header with a negative size in base-256, a header whose size is not a number, a name with a NUL (the prefix field), a NUL in a path of the manifest, an element of 300 bytes and a path of 6,000 bytes (the file system refuses: `RestoreWriteFailed`). Nothing got through. A manifest is read whole and capped at 64 MiB, so the entries it can list are bounded by its size (about 1.5 million directories: `TestCheckManifestOfManyEntries` checks 300,000 in 0.1 s), far below `maxEntryCount`.
- **The calls (D63–D65).**
  - *Membership.* The media server takes a user into a call only after the service checked that the user is a participant and may join (the handlers), and the call's two participants are fixed when it is made: a message is handled for the participant of its socket and no other, and only while that socket is the current one (`TestAStrangerCannotJoin`, `TestASecondSocketReplacesTheFirst`). What ends the access ends the call: a disabled user, any ended session of a participant, a password change and a reset end the user's calls in the same transaction and publish `call.ended` (`TestDisablingAUserEndsTheirCall`, `TestASessionEndingEndsTheCall`, `TestACallEndsWhenAnAccountChanges`), the socket checks its session at every ping (`TestAPingChecksTheSessionAgain`), and an expired session closes it with 4001. Direct conversations have no member who leaves, and the REST actions (`Answer`, `Decline`, `Cancel`, `HangUp`, `SetMedia`, `Join`, `Get`) each check the actor in the service (`TestCallsPermissions`: admin, member, non-member, disabled user).
  - *Parsing and size.* A message is at most 64 KiB (the read limit of the socket), must be one JSON object with a known type and no unknown field, an answer's `sdp` at most 32 KiB, a candidate line at most 2,048 bytes; an error never repeats the text. `FuzzSignalMessage` (`internal/calls/fuzz_test.go`, seeds in the test and in `internal/calls/testdata/fuzz/FuzzSignalMessage`) feeds the messages to the parser, the SDP to pion's SDP parser and to `SetRemoteDescription` of a real PeerConnection that has made its offer, and the candidates to `AddICECandidate`; the seeds are the messages of a real negotiation (the offer of the server, the answer of a pion client to it, its candidates) and broken variants. Run for 75 s with two workers: **72,490 executions, 65 interesting inputs, no failure** (each execution makes a PeerConnection, so the rate is lower than the key parsing's). Found: S16, no limit on how many messages and candidates a socket may send.
  - *The limits of D64.* Two participants: `TestAStrangerCannotJoin`. `-max-calls`: `TestCallsMaxCallsCountsOnlyOpenCallsOfTheProcess`. 2.5 Mbit/s of video: the bandwidth lines in the offer and REMB on the wire (`TestTwoClientsReceiveEachOthersMedia`). The ICE deadline: `TestICEThatNeverConnectsEndsTheCall`. The failed transport: `TestATransportThatFailsEndsTheCallAfterTheDeadline` (new; S17). The join deadline and the reconnect grace: `TestAParticipantWhoNeverJoinsFailsTheCall`, `TestAClosedSocketGetsTheReconnectGrace`.
  - *The media port.* It answers ICE only with credentials of a PeerConnection the server made: pion's UDP mux ignores a STUN message whose username has an unknown ufrag, and bytes that are not STUN go to no connection; its TCP mux closes a connection whose first packet is not a STUN binding request with a username within 30 seconds, and says nothing on the way. `TestTheMediaPortAnswersNothingToStrangers` sends the UDP port a binding request with an unknown ufrag, with an ufrag of one byte, with no colon, with a 800-byte username, with no username, with a broken length, 1,200 random bytes, DTLS-, RTP- and RTCP-shaped bytes, one byte, an empty datagram and one of 64,000 bytes, and the TCP port the same, framed as RFC 4571 and raw, and a silent connection: **not one byte comes back**, so the port cannot be used to amplify (an answer to a request with valid credentials is a few dozen bytes for a request of the same size or more), and afterwards the server still takes a call. Pion's messages are logged at debug level only.
  - *Shutdown.* `TestCloseLeavesNoGoroutine` and `TestCloseWhileACallIsRunningTellsTheClients` (22.1): every PeerConnection, socket and goroutine ends and is waited for; the relay's goroutine too (`TestAnEdgeThatStopsClosesItsSockets`).
  - *The relay through Redis (D65).* The envelopes carry the signalling only, never media. The edge process checks the user and the call (the handler asked the service) and rate-limits the socket; the home process drops an envelope for a call it does not hold, a participant that is not one, and a socket that was replaced (`TestTheRelayDropsWhatIsNotForACallOfTheHome`). **What a forged envelope can do** is for whoever can publish on the channel `clowder:calls:<process>`, i.e. whoever has access to Redis: an `EnvJoin` for a call that is open, with its real caller and callee, replaces the socket of that participant (the real one gets 4003) and receives the server's offer, so that person can take the participant's place in the call and hear and send the media; for a call that does not exist or is over the home asks the service and ends it at once (`subscribe` finds it not open), so nothing is made for a made-up ID. They can also end calls by sending `close` to an edge for a socket ID they know. As the event bridge of 1.1, this is inside the trust boundary of Redis (no password inside the compose network, the README says to give any other Redis a password, ACL and TLS); the envelopes are small JSON and the media never goes through Redis.

## Accepted risks and things to know (1.2)

- **A reset link logs in without the SSH code (SPEC §7.1, §7.16, D51).** The link is made by an admin and is a replacement for the password; it starts a session and the user's SSH code stays on for the next login (`TestSignUpAndResetNeverAskForTheCode` states it). So whoever gets the link (an admin's chat message, a shared screen) gets in without the second factor, and the SSH code does not protect against a stolen reset link. Asking for the code after a reset would change the flow for people who lost a password and, with it, a key, so the manager kept it as §7.16 decides (2026-10-29); the owner may revise. Handling: an admin turns the code off for a user who lost the key (`DELETE /admin/users/{id}/ssh-code`), the link lives 24 hours and is single use, and using it ends every other session.
- **Tries that race.** The limit of five wrong codes (and five wrong passwords, since 1.0) is checked before and counted after the work, so many requests sent at the same moment may all pass the check: a burst of N requests makes N tries, not five. At 40 bits a code is guessed by one try with a chance of 1 in 10^12, so even a thousand parallel tries are one in a billion, for the 60 seconds a code lives and only for someone who knows the password; the limiter holds after the burst.
- **An avatar costs memory while it is decoded.** A 4096 by 4096 PNG of 8-bit colour allocates 68 MB while it is decoded and scaled (133 ms), and one of 16-bit colour 132 MB (247 ms): `pictureSlots` lets two be decoded at once, so up to about 270 MB can be in use for a moment, over the 150 MB of an idle server (SPEC §10). The memory is the garbage collector's afterwards. Any logged-in user can do it. A lower limit of the size would change what the feature accepts; accepted by the manager (2026-10-29); the owner may lower `AvatarMaxPixels` (2048 by 2048 is a quarter).
- **A hostile archive can fill the disk.** `clowder restore` believes the sizes of the manifest as far as 1 PiB each (the checksum and the size are checked against what the archive holds, but a gzip of zeros is small, and tar can carry sparse files), so an archive made by an attacker can write until the disk is full; the target is removed when the restore fails, as for any failure. It is a command the operator runs on an archive they chose, into an empty directory. The README says to restore only archives you made.
- **The media port is reachable by everybody who can reach it, and the TCP side holds a connection for up to 30 seconds** before the first STUN message (a goroutine and a 512-byte buffer for each, no cap on the number: it is the file descriptors of the process). Put a firewall or the limits of the host in front of the port. Nothing is answered to a stranger (above).
- **A participant can send a lot of media to the other.** The server limits the video it asks for (REMB, 2.5 Mbit/s) but forwards what it gets; a sender who ignores REMB is forwarded as sent, up to what the connection allows. The call is between two people who agreed to it; either hangs up.
- **The call media is not end-to-end encrypted.** SRTP protects the hops; the server forwards and could see it (D63). Nothing is recorded.
- **Message sizes and rate on the API's WebSocket.** The WebSocket of the API (1.1) has the size limit of 16 KiB but, unlike the call socket (S16), no rate limit: a subscribe is a permission check and a database read. A user may hold 30 connections (D62). A flood is for the reverse proxy; a rate limit there is a recommendation for a later release.
- **The reset, pending and code routes are the pages' only unauthenticated writes**, each with the limiter of the login (a pending login with the code, a reset by token).
- **Processes of other users on the machine** can read the SSH host key if the data directory allows it; the data directory is 0750 and the key 0600, and the key is repaired when it is looser (S14).

## Out of scope (1.2)

- **The security of the browser's WebRTC stack, the camera and the microphone,** and the TLS of the reverse proxy in front of the pages (the media does not go through it).
- **A TURN server.** The server is the peer; a user behind a network that blocks both UDP and TCP to the media port cannot call.
- **The firewall of the host** for the SSH port, the media ports and the metrics (the README's table of ports says what to open).
- **Backups of PostgreSQL and Redis** (23.1 writes the files; the operator saves the database with `pg_dump`).
